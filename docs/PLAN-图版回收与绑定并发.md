## 一、P1-11 图版卡死回收（涉额度 · 待确认）

### 现在的链路

`artRestyle`（云函数内同步跑完生图全程）：

```
占 job 槽（reserving → running，CAS）
  → pay.consumeQuota 扣 1 次额度（免费优先、付费兜底）
  → await generateArt(...)   ← 10~60 秒，云函数就在这里被超时杀掉
  → 成功：写 job.status='done' + fileID + 回写票根 artVersion
  → 失败：写 job.status='failed' + pay.refundQuota 退 1 次
```

微信云函数最长 60 秒。**执行被杀时，后面两步都不会发生**，job 永远停在 `running`。用户遇到的是：

| # | 表现 | 用户会怎么说 |
|---|---|---|
| ① | 额度扣了、图没有、不退 | 「我的次数少了一次，图呢？」 |
| ② | `artQuery` 永远回 running → 前端转圈到 160 秒上限 | 「一直是正在作画」 |
| ③ | 该票有 running 的 job → 点「再画一次」直接返回 `queued`（防重入） | 「**这张票再也画不出来了**」 |

③ 是真正致命的：②的一次转圈还能忍，③ 是这张票被判了无期。

### 设计（懒回收：用户回来那一刻判定）

**判据** — `status === 'running'` 且 `updatedAt` 早于 `now - ART_JOB_STALE_MS`。
`ART_JOB_STALE_MS = 3 分钟`（云函数上限 60 秒，三倍余量；真在跑的活绝不可能超过它）。

**回收动作** — 条件更新抢占，抢到的这一次负责退额度：

```
where({ _id, status: 'running', updatedAt: _.lt(cut) })
  .update({ status: 'failed', msg: '上次没跑完，次数已退回，再点一次' })
```

`stats.updated === 1` 才算抢到 —— 并发轮询、用户连点，都只有一次能抢到，**只退一次**。

**退哪个池** — job 上补一个 `pool` 字段（消费成功时落），回收时按它精确退（PAY-3 的同一口径）。
本次改动之前留下的老 job 没有这个字段 → 走 `refundQuota` 既有的兼容反推分支，**不需要数据迁移**。

**顺带堵另一半** — 成功回写 `done` 也改成条件更新（`where({_id, status:'running'})`）。
否则一个已经被判失败并退过额的 job，可能被迟到的成功覆盖成 done —— 用户既拿到图、又拿回次数。
（60 秒超时下实际撞不上，但这是同一个 CAS 的另一半，一行的事。）

**回收的触发点（两个，都不新增定时任务）**

| 位置 | 时机 | 效果 |
|---|---|---|
| `artQuery` | 用户轮询时 | job 立刻变 failed → 前端显示「上次没跑完，次数已退回」+ 可重试 |
| `artRestyle` | 用户再点重绘时 | 先回收僵尸 job 再起新的，**③ 的「永久画不出来」被解开** |

不新增定时器：用户不回来的话，退不退额度对他没有意义；等他回来处理，既实时又省一套调度。
（REVIEW 里提的另一条路「任务表 + 定时触发器 + 真异步」成本高得多，留到生图变成主要成本项时再说。）

**前端**：**零改动**。`art.js` 的 `failed` 分支已经会显示服务端给的 msg 并提供「再画一次」。

### 额度口径（**这一条需要你拍板**）

1. **卡死一律退回一次**。理由：用户没拿到图。哪怕那次生图其实在云端跑成功了、只是回写没赶上，也退——多退一次的代价是几毛钱 AI 成本，少退一次的代价是用户觉得自己被骗。
2. **退回当初扣的那个池**（免费 / 付费），不是「随便还一个」。
3. 免费池跨月重置不受影响：回收发生在哪个月，就退到哪个月的账上（与现有 `refundQuota` 一致）。

## 二、P2-9 双人绑定并发（不涉额度 · 已实现）

**已修**（`bindAction` 的 `join` 分支）：

- **两人同时输同一个码**：绑定写入由裸 `doc(id).update` 改成条件更新 `where({_id, status:'waiting'})`，只有把 `waiting` 改成 `bound` 的那一次能成功；输的一方收到「这个邀请码刚被别人用了」。旧实现是后写覆盖先写——两边都看到「绑定成功」，文档里只留下后一个人。
- **同一个人连点两下**：第二次走幂等分支返回成功，不再显示「邀请码不存在」。
- **已绑好的人重进页面又输一次自己的码**：幂等成功，不再吓唬他「先解绑才能换人」。

**待拍板的那一半（一人同时在两份关系里）**：`join` 目前只拦「已绑定」，不拦「自己名下还有一条 waiting 的码」。
用户可以一边挂着自己的邀请码等别人加、一边加入别人的码 → 同时存在于两份 `couples` 文档，
而 `findMyCouple` 只取一条（`limit(1)`，没有排序）→ 我到底和谁绑着，是随机的。

注意一个现状：**未绑定时页面上没有「作废我的邀请码」的入口**（`duo.wxml` 的「解除绑定」只在 `bound` 时出现），
所以「先拦下来让你自己去取消」这条路，现在走不通。
