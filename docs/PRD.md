## 一、产品定位与价值

### 1.1 一句话定位

> 你的每一张票，都是一段时光的证据；有票为证，替你好好收着。

纸质票根数字化珍藏小程序 —— 把会褪色、易丢失的纸质票，变成可永久留存、可美好分享的「数字时光档案」。

### 1.2 三层价值

| 层级 | 价值 | 说明 |
|---|---|---|
| 功能价值 | AI 识别、修复、重绘 | 一键让模糊 / 破损 / 褪色的票根清晰重生，自动归档分类 |
| 情感价值 | 收藏的不是票，是记忆 | 收藏的是和某个人、在某个夜晚的自己——把「舍不得扔」变成「存得好看」 |
| 社交价值 | 私人记忆 → 可分享的数字票卡 | 让「我去过、我爱过、我在场」被温柔地看见 |

### 1.3 品牌角色与调性

- **角色**：一个温柔、细心、有点文艺的「时光收票员」——不打扰、懂纪念、帮你把回忆理成一本好看的册子
- **调性关键词**：温暖治愈 · 年轻文艺 · 仪式感 · 柔软可信
- **语气原则**：像朋友轻声说话，多用「你 / 我们」，少用功能腔；可以怀旧但不丧，可以可爱但不幼稚
- **Slogan（品牌全案口径）**：**时光不回头，票根存温柔**
- **辅助传播语（备选）**：把票根，存成时光 ／ 走过的，都有票为证 ／ 我在场，故我在
- **端上落地口径（2026-09-17 复核）**：分享标题与年报落款用「让时光有票为证」，纪念卡片落款用「有票为证 · 让时光有迹可循」，竖版素材图水印用「@有票为证 · 你的时光档案馆」——三处并存且都与品牌全案这句不同，**是否统一待拍板**

### 1.4 视觉与调性约束（做任何界面都要守）

|---|---|---|
| 奶油白 | `#FAF5EE` | 主背景 |

| 鹅黄 | `#F6DFA8` | 暖光点缀 |

- **辅助图形**：票根齿孔点列、邮戳圆环、日期印章、序列号、波浪销票线、微光星点、虚线路径
- **质感**：奶油纸感 + 明亮柔和日光 + 圆角卡片 + 大留白；界面保持原生控件层级，不把一切都卡通化
- **红线**：主标识不得拉伸 / 改色 / 旋转 / 加阴影；辅助图形不得喧宾夺主；邮政红只作小面积点缀

## 二、目标用户与角色

品牌全案圈定的五类人，他们打开小程序的那一刻各有各的心事：

| 角色 | 核心场景 | 情感诉求 | 沟通钩子 |
|---|---|---|---|
| 追星 / Livehouse 人群 | 演唱会、音乐节票根 | 在场证明、青春纪念 | 「那一夜我在现场」 |
| 电影爱好者 | 电影票、首映票 | 与某部作品的私人联结 | 「为这部电影留一张存根」 |
| 旅行党 | 车票、机票、门票 | 足迹与旅程轨迹 | 「走过的路，票都记得」 |
| 情侣 / 好友搭子 | 约会票、旅行票 | 共同记忆、关系仪式 | 「我们的第 N 张票」 |
| 文艺青年 | 展览、戏剧、书店 | 审美表达、生活归档 | 「把生活收进一本时光册」 |

**共性**：年轻、感性、有收藏欲、爱分享，吃「仪式感 + 审美在线」这一套，反感商务冷硬和粗糙的工具感。

## 三、用户故事

| # | 作为 | 我想要 | 以便 |
|---|---|---|---|
| US-1 | 刚看完演唱会的观众 | 拍一张票根就能自动认出场次、场馆、日期，不用手打 | 散场当晚就把那一夜存下来，不拖到票根丢进抽屉 |
| US-2 | 舍不得扔票根的人 | 把模糊、折痕、褪色的票根修清楚、甚至重画成画 | 纸会黄、字会淡，但我留住的那张还是好看的样子 |
| US-3 | 爱分享的人 | 把一张票根变成体面的卡片，存相册、发朋友圈 | 让「我去过、我在场」被温柔地看见，而不是晒一张皱票根 |
| US-4 | 和伴侣 / 好友一起看演出的人 | 两个人的票根合成一本共同收藏册，标出一起看过的场次和城市 | 有个地方替我们记着「我们的第 N 张票」 |
| US-5 | 旅行很多的人 | 一眼看见自己去过哪些城市、走过多少路 | 把零散的车票机票，变成一张属于自己的足迹地图 |
| US-6 | 有仪式感的人 | 年底有一份属于自己的年度回忆报告 | 有人替我总结这一年，而不是自己翻相册 |
| US-7 | 文艺青年 | 换一套顺眼的界面气质，慢慢整理我的收藏 | 用得舒服、看着好看，才愿意长期留下来 |
| US-8 | 赶时间的新用户 | 不注册不填资料，打开就能拍第一张票 | 第一次使用就有结果，不用先学怎么用 |

## 六、非功能需求

### 6.1 性能

| 项 | 要求 |
|---|---|
| 首屏 | 打开即见票根墙，无白屏；数据未到先出骨架屏 |
| 主包体积 | 不超过 2MB；大图走云存储或分包 |
| 列表 | 长列表滚动不卡顿；数据分批拉取，不因数量增长而超时 |
| 上传 | 照片上传前压缩（长边超过 1600 先压再传）；上传与识别过程有阶段化进度反馈 |
| 弱网 / 断网 | 有明确提示与兜底内容，不出现空白页 |

### 6.2 安全

- 内容安全见 CP-3；权限最小化见 CP-1；密钥管理见 CP-7；支付见 CP-8
- 用户数据的读写必须有归属校验，跨用户不可见

### 6.3 兼容

- iOS / Android 真机表现一致（图形、字体、字形回退）
- 深浅色主题下均不得出现不可读文字或穿帮图形
- 图片加载失败有占位兜底；低版本基础库不支持的能力要有降级路径

### 6.4 交付质量

- 每个功能必须有空态、加载态、失败态三态处理
- 改动必须配自动化回归用例，并在版本史中记录「改了什么 / 怎么验证 / 真机看什么」
- 当前回归基线：**48 套 / 1134 条全绿**（2026-09-20 实测）
- 自动化全绿不等于能用：开发者工具里看得见也不算数 —— 真机逐屏验收才是发布前最后一道（7.4.1 图形事故的教训）

## 七、范围外（明确不做）

| 不做 | 原因 |
|---|---|
| 独立账号体系（手机号 / 密码注册登录） | 微信内产品，授权即身份，多一套账号只增加流失与合规负担 |
| 站内社区、关注、评论、信息流 | 产品是私人收藏册，不是社交平台；分享走出小程序即可 |
| 票务交易、购票、电子票核销 | 存档已消费的票根是本分，进入交易会带来资质与售后重担 |
| 第三方票务平台数据自动抓取 | 涉及授权与数据合规，且票根的意义在于「亲手拍下来」 |
| 多端产品（H5 / App / PC 端） | 首期只做微信小程序，把单端体验做透 |
| 实体周边电商 | 属另立的商业线，不进本产品范围 |
| 位置打卡 / 定位签到 | 不申请定位权限（见 CP-6），城市信息以票面识别为准 |
